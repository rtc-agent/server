## 一、编码规范一致性

### 1.1 上下文键 (Context Key) 约定不一致

**严重程度**: Medium
**状态**: 未修复 (需要跨包重构,影响面较大)

项目已有统一的 `internal/infra/contextx` 包,使用未导出 struct 类型 `contextKey{ name string }` 作为键:
```go
// internal/infra/contextx/keys.go
type contextKey struct{ name string }
var userIDKey = contextKey{"user_id"}
```

但 OSS3 在 `oss3_middleware.go` 中使用了不同的键类型:
```go
type contextKey string  // 使用 string 而非 struct
const ContextKeyUserID contextKey = "user_id"
```

**差异点**:
- 类型不同: 项目用 `struct`,OSS3 用 `string`
- 可访问性: 项目键未导出,通过函数封装;OSS3 键已导出为常量
- 包位置: 项目在 `contextx` 包集中管理;OSS3 分散在 handler 包

**风险**: 两套键体系可能让维护者困惑。但由于 OSS3 的 `user_id` 含义与 contextx 的 `uuid.UUID` user_id 不同(string vs UUID),分离有其合理性。

**建议**: 在 oss3_middleware.go 的 contextKey 定义处添加注释说明与 contextx 的区分理由。

### 1.2 Package 命名规范

**严重程度**: Low
**状态**: 未修复

目录名 `rtc-oss3` 使用连字符,在 Go 中不常见。包内声明的包名为 `rtcoss3`,导入别名也是 `rtcoss3`。虽然功能正确,但目录名与包名不一致可能导致 goimports 工具行为不一致。

**建议**: 考虑将目录重命名为 `rtcoss3`(无连字符),与包名完全一致。这不影响功能,但更符合 Go 社区惯例。

### 1.3 错误信息格式不统一

**严重程度**: Low
**状态**: 未修复

项目其他模块的错误格式:
```go
return fmt.Errorf("get user: %w", err)
```

OSS3 中的错误格式:
```go
return fmt.Errorf("user %s: %w", userID, rtcoss3.ErrQuotaExceeded)  // oss3_quota.go
return fmt.Errorf("minio %s: %w", operation, ErrBackendKeyNotFound)  // minio_backend.go
```

`oss3_quota.go` 中将 userID 嵌入错误消息,而其他地方不包含用户标识。这在日志中可能导致信息泄露或格式不一致。

**建议**: 统一错误格式,用户标识应通过日志字段传递,不嵌入错误消息。

### 1.4 日志级别使用

**严重程度**: Low
**状态**: 部分修复

SigV4 中间件使用 `logger.Info` 记录请求到达,但包含 Authorization 头内容。已降级为 `logger.Debug` 并移除 auth_header。

但 `mapMinIOError` 中的 `logger.Debug(context.Background(), ...)` 使用了 `context.Background()` 而非传递请求上下文。这导致追踪链路断裂。

**建议**: `mapMinIOError` 应接受 `ctx context.Context` 参数,或使用 zap 的 skip caller 模式避免 context 依赖。

## 三、实现细节问题

### 3.1 [Critical] Authorization 头内容日志泄露

**严重程度**: Critical
**状态**: ✅ 已修复

**文件**: `internal/handler/http/oss3_sigv4.go:35`

```go
// 修复前
logger.Info(r.Context(), "SigV4 middleware: request received",
    zap.String("auth_header", r.Header.Get("Authorization")[:min(20, len(...))]))

// 修复后
logger.Debug(r.Context(), "SigV4 middleware: request received",
    zap.String("method", r.Method),
    zap.String("path", r.URL.Path))
```

前 20 字符包含 `"AWS4-HMAC-SHA256 Cre"` 加上 AccessKeyID 的前 3 个字符,可能泄露凭据信息。在生产环境中,即使是部分 Authorization 头也不应被记录。

### 3.2 [Critical] LookupCredential 无法区分"未找到"与"数据库错误"

**严重程度**: Critical (影响可用性)
**状态**: ✅ 已修复

**文件**: `internal/usecase/oss3_credential_cache.go:62-65`

```go
// 修复前: DB 错误和未找到都返回 nil, nil
if err != nil {
    return nil, nil  // 无法区分!
}

// 修复后: 区分 gorm.ErrRecordNotFound 和实际 DB 错误
if err != nil {
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, nil
    }
    return nil, fmt.Errorf("lookup credential %q: %w", accessKeyID, err)
}
```

**影响**: 修复前,数据库暂时不可用时,所有请求都返回 403 (签名无效),而非 500 (内部错误),客户端无法通过重试恢复。修复后,实际 DB 错误返回 500,客户端可以重试。

### 3.3 SigV4 签名实现 — 重复查询参数处理

**严重程度**: High
**状态**: 建议修复

**文件**: `pkg/rtc-oss3/sigv4.go:314-341`

`canonicalQueryString` 使用 `url.Values`(即 `map[string][]string`),当 URL 中有重复参数(如 `?a=1&a=2`)时,Go 的 `url.ParseQuery` 会将其合并为 `map["a"] = ["1", "2"]`。代码对 values 进行了排序并分别输出,但 AWS SigV4 规范要求**保留原始顺序中的每个 `key=value` 对**。

**测试已发现此问题** (sigv4_edge_test.go:258):
```go
// url.ParseQuery groups duplicate keys, sorted values: ["1","2"]
// Per AWS spec, each value gets its own key= prefix
{"DuplicateKeys", "a=2&a=1", "a=1&a=2"},
```

对于大多数 S3 客户端,不会产生重复参数,所以实际影响有限。但如果需要严格兼容 AWS SigV4,应使用 `url.QueryUnescape` + 手动解析保留原始顺序。

### 3.4 SigV4 Authorization Header 解析 — 额外逗号漏洞

**严重程度**: High
**状态**: 建议修复

**文件**: `pkg/rtc-oss3/sigv4.go:136-178`

`ParseAuthorizationHeader` 使用 `strings.Split(auth[17:], ", ")` 分割,但测试已发现额外逗号不会被拒绝:
```go
// sigv4_edge_test.go:177
{"ExtraCommas", "AWS4-HMAC-SHA256 Credential=...aws4_request,, SignedHeaders=host, Signature=abc", false},
```

注释已标记 "BUG",但修复被推迟。恶意客户端可构造带有额外逗号的头部,可能导致 credential 中包含尾随逗号,从而绕过签名验证。

**建议**: 对解析后的各 part 进行 trim 和格式校验。

### 3.5 handlePutObject 中 err 变量的 defer 语义

**严重程度**: High
**状态**: 建议修复

**文件**: `internal/handler/http/oss3.go:243-284`

```go
quotaRequestID, err := h.oss3UC.CheckAndReserveQuota(...)
defer func() {
    if err != nil {
        h.oss3UC.ReleaseQuota(...)
    }
}()

// Upload to backend
etag, err := h.oss3UC.Backend().PutObject(...)  // err 赋值

// Commit quota (注意: 使用 if err = ,不是 :=)
if err = h.oss3UC.CommitQuota(...); err != nil {
    logger.Warn(...)  // err 保持非 nil
}

// Create file record
err = h.oss3UC.PutObjectWithComp(...)  // 可能覆盖 err
```

**问题**: 如果 `CommitQuota` 成功(err = nil),但 `PutObjectWithComp` 失败(err != nil),defer 会调用 `ReleaseQuota`。但此时 quota 已经被 commit 了!ReleaseQuota 会删除已不存在的 pending key (no-op),但语义上令人困惑。

如果 `CommitQuota` 失败(err != nil),defer 会 `ReleaseQuota`,这是正确的行为 (pending key 可能还在)。

**建议**: 添加注释说明 err 变量的生命周期和 defer 的意图。或改为使用独立的 bool 标志:
```go
quotaCommitted := false
...
if err = h.oss3UC.CommitQuota(...); err == nil {
    quotaCommitted = true
}
```

### 3.12 缺少请求体大小限制

**建议**: 使用 `http.MaxBytesReader` 限制请求体,或在 quota 检查阶段设置上限。

### 3.13 Range 下载的后缀范围处理

**严重程度**: Medium
**状态**: 未修复

**文件**: `internal/handler/http/oss3.go:719-726`

```go
if parts[0] == "" {
    // Suffix range: "-500" means last 500 bytes
    suffixLen, err := strconv.ParseInt(parts[1], 10, 64)
    if err != nil {
        return 0, 0, false, err
    }
    return -suffixLen, -1, true, nil

```

后缀范围返回 `(-suffixLen, -1, true, nil)`,但 `handleGetObject` 将此直接传给 `GetObjectRange(ctx, bucket, key, start, end)`,MinIO 的 `SetRange(start, end)` 可能不支持负数 start。

**建议**: 先 HeadObject 获取文件大小,计算实际 start = fileSize - suffixLen,再传给 GetObjectRange。

- 充分的边缘测试 (空 payload、大 payload、篡改、过期、错误密钥)

### 4.5 资源清理

愿每一行代码都经得起推敲,愿每一次提交都让系统更加可靠。
