### 5. 安全问题

**发现的问题**:

#### [HIGH] handleGetObject 中 Close goroutine 使用已取消的 r.Context()
- **位置**: `oss3.go:460-477`
- **问题**: 当客户端断开连接时，`r.Context()` 被取消。defer 中的 goroutine 使用 `r.Context()` 记录日志，可能导致 Warn 消息被 logger 丢弃。更严重的是，如果 `Close()` 永久阻塞，goroutine 泄漏。
- **严重程度**: HIGH
- **修复状态**: ✅ 已修复
- **修复说明**: 
  1. goroutine 内改用 `context.Background()` 记录日志，确保 Warn 不被丢弃
  2. 添加注释说明 goroutine 泄漏的最坏情况受 MinIO Transport 超时约束

#### [MEDIUM] parseS3Path 的 ".." 检查过于宽泛
- **位置**: `oss3.go:146`
- **问题**: `strings.Contains(path, "..")` 会拒绝合法文件名如 `my..file.txt`。虽然上游 `ValidateKey` 严格限制 key 格式（`user-{uuid}/{md5}.{ext}`），使此问题实际不会触发，但作为纵深防御层，应精确拒绝路径遍历模式
- **严重程度**: MEDIUM
- **修复状态**: ✅ 已修复
- **修复说明**: 改为精确匹配路径遍历模式：`..`、`../`、`/..`、`/../`，允许 ".." 作为文件名字串

#### [MEDIUM] parseRangeHeader 对 "-0" 和 "bytes=-" 处理不健壮
- **位置**: `oss3.go:1129-1176`
- **问题**: 
  1. "bytes=-0" 返回 (0, -1, true, nil)，后续 GetObjectRange(0, -1) 行为未定义
  2. "bytes=-" 被解析为 suffixLen=0，同样导致无效范围
  3. RFC 7233 §2.1 要求 suffix-length >= 1
- **严重程度**: MEDIUM
- **修复状态**: ✅ 已修复
- **修复说明**: 
  1. 改用 `strings.Count(rangeSpec, "-") != 1` 严格拒绝多 dash
  2. 显式拒绝 `suffixLen <= 0` 和空 suffix
  3. 添加 RFC 7233 引用
  4. 添加对应测试用例

#### [MEDIUM] KeyPattern 假设 userID 为 UUID 格式
- **位置**: `pkg/rtc-oss3/key_validation.go:13`
- **问题**: `keyPattern = regexp.MustCompile(`^user-[a-f0-9-]{36}/...`)` 硬编码 UUID 格式（36 字符）。若未来 userID 格式变化，所有 key 校验都会失败
- **严重程度**: MEDIUM（隐藏依赖）
- **修复状态**: ❌ 未修复
- **修复说明**: 需要在 `key_validation.go` 顶部添加注释，明确说明此假设。建议后续通过配置注入 user ID pattern

### 7. 分布式系统风险

**发现的问题**:

#### [MEDIUM] ReconcileQuota 可能覆盖 pending reservation
- **位置**: `oss3_reconcile.go:149-185`
- **问题**: 当 reconciliation 运行时，如果某用户有 pending reservation（尚未 commit 或 rollback），`setRedisQuota(dbSum)` 会覆盖当前 quota 计数器。pending key 仍然存在，但 quota 计数器被重写。下一次 reservation 检查 `current + pending + amount > maxQ`，其中 current 被覆盖，可能导致配额计算偏差
- **严重程度**: MEDIUM
- **修复状态**: ❌ 未修复（设计取舍）
- **修复说明**: 实际影响有限：
  1. pending TTL 5 分钟，reconcile 间隔 1 小时，重叠窗口小
  2. 即便重叠，下一次 commit 会正确更新 quota
  3. 建议在 `setRedisQuota` 前加日志记录 pending keys 数量

#### [MEDIUM] LuaQuotaReserve 非幂等
- **位置**: `internal/infra/cache/oss3_lua.go:32-45`
- **问题**: 若相同 requestID 被调用两次（理论上 UUID 碰撞不可能，但网络重试可能），pending 会被覆盖，quota 检查基于已被修改的 pending 值
- **严重程度**: MEDIUM
- **修复状态**: ❌ 未修复
- **修复说明**: 实际风险极低（UUID v4 碰撞概率 < 1e-37）。CommitQuota 的 SETNX 幂等保护已覆盖此场景

#### [HIGH] 批量删除缺少 DB 重试
- **位置**: `oss3.go:940-950`
- **问题**: `handleDeleteObjects` 批量删除成功后，DB 记录删除无重试机制。而单条 `handleDeleteObject` 有 3 次重试。不一致
- **严重程度**: HIGH
- **修复状态**: ❌ 未修复（建议后续补充）
- **修复说明**: 批量删除中每条记录的 DB 删除应使用相同的 `dbRetryDelays` 重试模式。建议重构为 `deleteFileRecordWithRetry` 辅助函数
